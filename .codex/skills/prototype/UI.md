# UIプロトタイプ

1つのルート上で**根本的に異なる複数のUIバリエーション**を生成し、フローティング下部バーから切り替え可能にする。ユーザーはブラウザでバリアントを切り替え、1つを選ぶ（またはそれぞれから一部を借用し）、残りを捨てる。

質問が見た目ではなくロジック/状態に関する場合 — 間違ったブランチ。[LOGIC.md](LOGIC.md)を使用。

## これが適切な形状の場合

- 「このページはどう見えるべきか？」
- 「コミットする前にこのダッシュボードのいくつかの選択肢を見たい。」
- 「設定画面の異なるレイアウトを試して。」
- ユーザーが頭の中の3つの曖昧なモックアップの間で1日費やすことになりそうな場合。

## 2つのサブ形状 — サブ形状Aを強く推奨

UIプロトタイプは**アプリの他の部分と隣り合わせ**の方がはるかに判断しやすい — 本物のヘッダー、本物のサイドバー、本物のデータ、本物の密度。使い捨てルート単体は真空状態：すべてのバリアントが独立していればまともに見える。デフォルトはサブ形状Aを、バリアントをホストできる既存のページがもっともらしく存在する場合に選択。プロトタイプが本当に近くに居場所がない場合のみサブ形状Bに。

### サブ形状A — 既存ページへの調整（推奨）

ルートは既に存在。バリアントは**同じルート上**でレンダリングされ、`?variant=` URL検索パラメータでゲートされる。既存のデータフェッチ、パラメータ、認証はすべて残る — レンダリングだけが切り替わる。これがデフォルト。特定の理由がない限りこれを選ぶ。

プロトタイプがまだページを持たないものの、*当然既存のページの中に存在するもの*（ダッシュボードの新しいセクション、設定画面の新しいカード、既存フローの新しいステップ）の場合 — それもサブ形状A。バリアントをホストページの中にマウントする。

### サブ形状B — 新しいページ（最後の手段）

プロトタイプ対象が本当に既存のページの中に組み込めない場合にのみ使用 — 例：全く新しいトップレベルの画面、またはどこにも組み込めないフロー。

プロジェクトが既に使用するルーティング規約に従った**使い捨てルート**を作成 — 新しいトップレベル構造を発明しない。名前は明らかにプロトタイプと分かるように（例：パスやファイル名に`prototype`を含める）。同じ`?variant=`パターン。

サブ形状Bを確定する前に健全性チェック：本当に組み込める既存のページはないか？ 空のルートは、内容のあるページが露呈する設計上の問題を隠す。

両方のサブ形状でフローティング下部バーは同じ。

## プロセス

### 1. 質問を記述しNを選択

デフォルトは**3バリアント**。5を超えると根本的に異なるものではなくなり、ノイズになる — そこで上限。

プロトタイプの場所またはファイル先頭のコメントに1行で計画を書き下す：

> 「設定ページの3つのバリアント、`?variant=`で切り替え、既存の`/settings`ルート上。」

これはユーザーがその場にいてもいなくても機能する。

### 2. 根本的に異なるバリアントを生成

各バリアントをドラフト。次に従う：

- ページの目的とアクセス可能なデータ。
- プロジェクトのコンポーネントライブラリ / スタイリングシステム（TailwindCSS、shadcn、MUI、プレーンCSS、その他）。
- 明確なエクスポートコンポーネント名。例：`VariantA`、`VariantB`、`VariantC`。

バリアントは**構造的に異なる**必要がある — 異なるレイアウト、異なる情報階層、異なる主要アフォーダンス。単なる色違いではない。微妙に調整したカードグリッドが3つあるのはUIプロトタイプではなく、壁紙。2つのドラフトが似すぎている場合、「カードグリッドを使用しない」という明示的な指示で1つをやり直す。

### 3. 配線する

ルート上に単一のスイッチャーコンポーネントを作成：

```tsx
// 疑似コード — プロジェクトのフレームワークに合わせる
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

サブ形状A（既存ページ）の場合：スイッチャーの上に既存のデータフェッチをすべて保持。バリアントごとに変わるのはレンダリングされたサブツリーのみ。

サブ形状B（新しいページ）の場合：`/prototype/<name>`の使い捨てルートが同じスイッチャーをマウント。

### 4. フローティングスイッチャーを構築

画面の下部中央に固定配置の小さなバー。3つの要素：

- **左矢印** — 前のバリアントにサイクル（ラップアラウンド）。
- **バリアントラベル** — 現在のバリアントキーと、バリアントが名前をエクスポートしている場合はその名前も表示。例：`B — サイドバーレイアウト`。
- **右矢印** — 次にサイクル（ラップアラウンド）。

動作：

- 矢印のクリックはURL検索パラメータを更新（フレームワークのルーターを使用 — Nextなら`router.replace`、React Routerなら`navigate`など）。バリアントが共有可能でリロード後に安定するように。
- キーボード：`←`と`→`の矢印キーもサイクル。`<input>`、`<textarea>`、`[contenteditable]`がフォーカスされている時は矢印キーをインターセプトしない。
- ページと視覚的に区別（例：高コントラストのピル、控えめなシャドウ）。評価中のデザインの一部ではないことが明確。
- 本番ビルドでは非表示 — `process.env.NODE_ENV !== 'production'`または同等のチェックでゲート。うっかりしたプロトタイプのマージがバーをユーザーに出荷しないように。

スイッチャーを単一の共有コンポーネントにして、両方のサブ形状で再利用可能に。プロジェクトで共有UIが置かれている場所に配置。

### 5. 引き渡す

URL（と`?variant=`キー）を提示。ユーザーは時間ができたら切り替える。興味深いフィードバックは通常 **「BのヘッダーとCのサイドバーが欲しい」** — それが実際に欲しいデザイン。

### 6. 答えをキャプチャして片付ける

バリアントが勝者になったら、どれとその理由を書き留める（コミットメッセージ、ADR、イシュー、またはユーザーが応答していない場合はプロトタイプの隣の`NOTES.md`）。その後：

- **サブ形状A** — 負けたバリアントとスイッチャーを削除。勝者を既存ページに折り込む。
- **サブ形状B** — 勝ったバリアントを本物のルートに昇格。使い捨てルートとスイッチャーを削除。

バリアントコンポーネントやスイッチャーを放置しない。すぐに腐り、次の読者を混乱させる。

## アンチパターン

- **色やコピーだけが異なるバリアント。** それは微調整であり、プロトタイプではない。本物のバリアントは構造について意見が異なる。
- **バリアント間でコードを共有しすぎる。** 共有の`<Header>`は可。共有の`<Layout>`は目的を損なう。各バリアントはレイアウトを投げ捨てる自由を持つべき。
- **バリアントを実際のミューテーションに配線する。** 読み取り専用プロトタイプは問題ない。バリアントがミューテートする必要がある場合、スタブに向ける — 質問は「これはどう見えるべきか」であり、「バックエンドは動くか」ではない。
- **プロトタイプをそのまま本番に昇格させる。** バリアントコードはプロトタイプの制約下で書かれた（テストなし、最小限のエラー処理）。折り込む際は適切に書き直す。
