## ドメイン認識

コードベース探索中に、既存のドキュメントも探す：

### ファイル構造

ほとんどのリポジトリは単一のコンテキストを持つ：

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

ルートに`CONTEXT-MAP.md`が存在する場合、リポジトリは複数のコンテキストを持つ。マップは各コンテキストの場所を示す：

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← システム全体の決定
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← コンテキスト固有の決定
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

ファイルは遅延して作成 — 書き込む内容がある場合のみ。`CONTEXT.md`が存在しない場合、最初の用語が解決されたときに作成する。`docs/adr/`が存在しない場合、最初のADRが必要になったときに作成する。

## セッション中

### 用語集に対する検証

ユーザーが`CONTEXT.md`の既存の言語と矛盾する用語を使用した場合、すぐに指摘する。「用語集では'キャンセル'をXと定義していますが、Yを意味しているようです — どちらですか？」

### 曖昧な言語の鋭敏化

ユーザーが曖昧または多重に使われる用語を使用した場合、正確な正規用語を提案する。「あなたは'アカウント'と言っていますが、顧客のことですか、ユーザーのことですか？ それらは別のものです。」

### 具体的なシナリオの議論

ドメインの関係性が議論されている場合、具体的なシナリオでストレステストする。エッジケースを探り、概念間の境界についてユーザーに正確な指定を強いるシナリオを考案する。

### コードとの相互参照

ユーザーが何かの動作を述べた場合、コードがそれに同意しているか確認する。矛盾が見つかった場合、表面化させる：「コードでは注文全体をキャンセルしていますが、部分キャンセルが可能だと言いましたね — どちらが正しいですか？」

### CONTEXT.mdのインライン更新

用語が解決されたら、その場で`CONTEXT.md`を更新する。まとめて後でやらない — 発生した瞬間にキャプチャする。[CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md)のフォーマットを使用。

`CONTEXT.md`には実装の詳細を一切含めない。`CONTEXT.md`を仕様書、スクラップパッド、または実装決定のリポジトリとして扱わない。これは用語集であり、それ以上ではない。

### ADRの控えめな提案

次の3つがすべて真の場合にのみADRの作成を提案：

1. **元に戻すのが難しい** — 後で考えを変えるコストが意味のある大きさ
2. **文脈なしでは驚くべきもの** — 未来の読者は「なぜこんなやり方をしたのか？」と思うだろう
3. **実際のトレードオフの結果** — 本当の代替案があり、特定の理由で1つを選んだ

3つのいずれかが欠けている場合、ADRはスキップ。[ADR-FORMAT.md](./ADR-FORMAT.md)のフォーマットを使用。
