# Goコードレビューガイドライン

このスキルは、Goで書かれたバックエンドコードの変更点（Diff）を目視レビューする際の手順とチェックリストを提供します。静的解析や自動テストでは検知できない設計、イディオム、アーキテクチャ境界の遵守状況を検証します。

---

## 1. レビューの流れ

Go関連のファイル（`*.go`）に変更があった場合、以下の手順でレビューを実施してください。

1. **差分（Diff）の取得**: コミット前の作業コピーや特定のコミット/ブランチとの比較において、`git diff`（またはステージング済みの差分を確認する `git diff --cached` や、特定のブランチと比較する `git diff origin/main` など）を実行して変更差分を取得します。
2. **変更全体の把握**: 差分からどのコンポーネント（Domain, Usecase, Repository, Utils）が追加・変更されたかを確認します。
3. **差分の目視レビュー**: 取得した `git diff` の出力結果に基づき、後述の**レビューチェックリスト**に照らし合わせてコードの一行一行を精査します。
4. **指摘事項の整理**: 問題を発見した場合、改善案となる「具体的な修正コード例」を合わせて作成します。
5. **レビュー結果の報告**: 後述の**出力テンプレート**に従い、結果をユーザーに報告します。

## 2. レビューチェックリスト

### 2.1 アーキテクチャとレイヤー構造（プロジェクトルール）
*   [ ] **レイヤー境界の遵守**: 依存関係は内側（Domain）に向かってのみ流れているか。逆方向の依存や循環参照がないか。
    *   **Domain (`internal/domain`)**: ビジネスロジックの核。他レイヤー（Usecase, Repository）に依存していないか。
    *   **Usecase (`internal/usecase`)**: ユースケースの実現。`domain` にのみ依存し、具象 `repository` に依存していないか。リポジトリインターフェースをこのレイヤーで定義しているか。
    *   **Repository (`internal/repository`)**: 外部アクセス。`usecase` で定義されたインターフェースを具象実装し、`domain` および `usecase` にのみ依存しているか。
    *   **Utils (`internal/utils`)**: 横断的関心事（ログ等）。他レイヤーのビジネスロジックに依存していないか。

### 2.2 エラーハンドリング（プロジェクトルール ＆ 一般ルール）
*   [ ] **Wailsハンドラーの戻り値**: フロントエンドに直接公開されるメソッド（`app.go` 内）は、エラー発生時に必ず `*dto.AppError` を返しているか。
*   [ ] **エラーのラッピング**: パッケージ内部やユースケース層でエラーを呼び出し元に伝播する際、`fmt.Errorf("context message: %w", err)` を使用して `%w` でラップしているか（`%v` ではなく `%w`）。
*   [ ] **エラーログの記録**: 呼び出し元にエラーを返す前に、必要に応じて `logger.Error` でコンテキスト情報とともに記録しているか。
*   [ ] **エラー文字列のスタイル**: エラーメッセージの文字列は小文字で始まり、末尾に句読点（ピリオドや改行）を含んでいないか（例: `fmt.Errorf("failed to fetch session")` は良、`"Failed to fetch session."` は悪）。
*   [ ] **エラーの等価判定**: エラーの等価比較において、`err == os.ErrNotExist` のような直接比較ではなく `errors.Is(err, os.ErrNotExist)` を使用しているか。
*   [ ] **成功時の戻り値**: 正常終了時にエラーインターフェースに値を返す場合、明示的に `nil` を返しているか。

### 2.3 ロギング（プロジェクトルール）
*   [ ] **専用ロガーの利用**: 標準 `log` パッケージや `slog` パッケージを直接使用せず、必ず `codex-session-display/internal/utils/logger` パッケージを使用しているか。
*   [ ] **ログレベルの使い分け**: 事象の深刻度に合わせて適切なレベルを使用しているか。
    *   `Debug`: 開発用詳細情報（引数、中間結果）。
    *   `Info`: システムの主要な状態変化（起動、終了、ユースケース完了）。
    *   `Warn`: 処理継続可能だが注意が必要な事象（tolerantパースでのレコードスキップなど）。
    *   `Error`: 復旧不可能・主要機能の動作不能（ファイル読み込み失敗など）。
*   [ ] **構造化ログの形式**: ログ出力時にキーと値のペアを用いて文脈情報を持たせているか（例: `logger.Info("ListSessions completed", "count", len(res))`）。

### 2.4 Goのイディオムとスタイル（一般ルール）
*   [ ] **スライスの空判定**: スライスが空であるかどうかのチェックに `len(s) == 0` を使用しているか（`s == nil` は空スライスを見落とすため避ける）。
*   [ ] **スライスの容量指定**: スライスの長さが事前に判明している場合、`make([]T, 0, cap)` を使用してメモリ再割り当てを最小限に抑えているか。
*   [ ] **頭字語（Initialisms）の表記**: `ID`, `URL`, `API`, `HTTP` などの頭字語はすべて大文字、またはすべて小文字で表記されているか（例: `sessionID` は良、`sessionId` は悪）。
*   [ ] **構造体メソッドの集約**: 構造体のフィールドを利用したロジックが、呼び出し側ではなく構造体のメソッドとして定義されているか（ドメインロジックの集約）。
*   [ ] **グローバル正規表現コンパイル**: `regexp.MustCompile` が関数の実行ごとに呼ばれず、パッケージグローバル変数として事前に一度だけコンパイルされているか。
*   [ ] **ネストの削減（アーリーリターン）**: エラー条件やガード句を最初にチェックして早期にリターン（`return` / `continue`）することで、ネストを浅く保っているか。
*   [ ] **不要なelseブロックの排除**: `if` ブロックが `return` 等で終わる場合、不要な `else` を繋げずに記述しているか。
*   [ ] **レシーバ名の一貫性**: レシーバ変数は `this` や `self` ではなく、型名から連想される1〜2文字の短い名前（例: `s *sessionRepo`）を使用しているか。

### 2.5 ユニットテスト（プロジェクトルール ＆ 一般ルール）
*   [ ] **テストファイルの配置**: テスト対象ファイルと同一のディレクトリに `*_test.go` として配置されているか。
*   [ ] **Table-Driven Test (TDT) の利用**: 複数のテストケースを検証する際、テーブル駆動テストの構造を採用しているか。
*   [ ] **`assert` と `require` の使い分け**: テスト失敗時に実行を停止すべき前提条件（エラー有無、スライスの長さ確認等）には `require.X` を使い、その後のアサーションには `assert.X` を使っているか（nil pointer panic の防止）。
*   [ ] **アサーション関数の引数順序**: `assert.Equal` や `require.Equal` で `(t, expected, actual)` の順で引数を渡しているか。
*   [ ] **適切な検証関数の選択**: `assert.Equal(t, nil, err)` ではなく `assert.NoError(t, err)` など、型安全で意図の明確な検証関数を使用しているか。
*   [ ] **検証メッセージの付与**: 複雑な検証や複数のアサーションがある場合、アサーション関数にオプションのメッセージ（`msgAndArgs`）を渡して意図を明確にしているか。

## 3. レビュー結果の出力テンプレート

レビュー結果を報告する際は、以下のフォーマットをそのまま適用して出力してください。

```markdown
# Goコードレビュー結果

## 概要
[ここにレビュー対象のブランチ/コミット/変更内容の全体的な要約を記述]

## 指摘事項
[問題が見つからなかった場合は「指摘事項はありません」と記述]

### 1. [指摘カテゴリ（例: エラーハンドリング）]
*   **ファイル**: [ファイル名と行数へのリンク（例: internal/repository/session_fs.go#L120-L125）]
*   **問題点**: [何がルールに違反しているか、なぜ修正すべきかの理由]
*   **修正コード例**:
    ```go
    // [ここに修正後の具体的なコード例]
    ```

---
[必要に応じて指摘事項を繰り返します]
```
