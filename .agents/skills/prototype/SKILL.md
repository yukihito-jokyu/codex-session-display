# プロトタイプ

プロトタイプは**質問に答える使い捨てコード**。質問が形状を決定する。

## ブランチの選択

どの質問に答えるのかを特定 — ユーザーのプロンプト、周囲のコード、またはユーザーがいる場合は尋ねる：

- **「このロジック / 状態モデルは正しいか？」** → [LOGIC.md](LOGIC.md)。紙上で推論しにくいケースを状態マシンに通す、小さなインタラクティブターミナルアプリを構築。
- **「これはどう見えるべきか？」** → [UI.md](UI.md)。1つのルート上で、URL検索パラメータとフローティング下部バーで切り替え可能な、根本的に異なる複数のUIバリエーションを生成。

2つのブランチは非常に異なる成果物を生成 — これを間違えるとプロトタイプ全体が無駄になる。質問が本当に曖昧でユーザーに連絡がつかない場合、周囲のコードに最も合致するブランチをデフォルトにし（バックエンドモジュール → ロジック、ページやコンポーネント → UI）、プロトタイプの先頭に仮定を記す。

## 両方に適用されるルール

1. **初日から使い捨てとして、明確にマーク。** プロトタイプコードは、実際に使用される場所の近く（プロトタイプの対象となるモジュールやページの隣）に配置して文脈を明確にする — ただし、普通の読者がプロトタイプだと分かるように命名。使い捨てUIルートの場合、プロジェクトが既に使用するルーティング規約に従う。新しいトップレベル構造を発明しない。
2. **1コマンドで実行。** プロジェクトの既存のタスクランナーがサポートするもの — `pnpm <name>`、`python <path>`、`bun <path>`など。ユーザーは考えずに起動できる必要がある。
3. **デフォルトで永続化なし。** 状態はメモリに存在。永続化はプロトタイプが_チェックしている_ものであり、依存すべきものではない。質問が明示的にデータベースを含む場合、スクラッチDBや「PROTOTYPE — 消して」という明確な名前のローカルファイルを使用。
4. **磨きはスキップ。** テストなし、プロトタイプを_実行可能_にする以上のエラー処理なし、抽象化なし。重要なのは早く何かを学んでから削除すること。
5. **状態を表面化。** 各アクション（ロジック）または各バリアント切り替え（UI）の後、完全な関連状態を表示またはレンダリングして、ユーザーが何が変わったかを見えるようにする。
6. **完了時に削除または吸収。** プロトタイプが質問に答えたら、削除するか、検証された決定を実際のコードに折り込む — リポジトリに腐らせない。

## 完了時

プロトタイプから価値があるのは_答え_だけ。回答していた質問とともに、耐久性のある場所（コミットメッセージ、ADR、イシュー、またはプロトタイプの隣の`NOTES.md`）にキャプチャする。ユーザーがいる場合、キャプチャは短い会話。いない場合、プレースホルダーを残して、彼ら（または次のパスのあなた）がプロトタイプを削除する前に判定を記入できるようにする。
