# ロジックプロトタイプ

ユーザーが手動で状態モデルを操作できる小さなインタラクティブターミナルアプリ。質問が**ビジネスロジック、状態遷移、またはデータの形**に関する場合に使用 — 紙上では合理的に見えるが、実際のケースを通してみると初めて違和感が出る種類のもの。

## これが適切な形状の場合

- 「この状態マシンがXの後にYというエッジケースを処理するか確信がない。」
- 「このデータモデルで本当に...の場合を表現できるのか？」
- 「書き始める前にAPIがどうあるべきか手で触って確かめたい。」
- ユーザーが**ボタンを押して状態の変化を見たい**あらゆる場合。

質問が「これはどう見えるべきか」の場合 — 間違ったブランチ。[UI.md](UI.md)を使用。

## プロセス

### 1. 質問を記述

コードを書く前に、プロトタイプの対象となる状態モデルと質問を書き下す。プロトタイプのREADMEまたはファイルの先頭のコメントに1段落で。間違った質問に答えるロジックプロトタイプは純粋な無駄 — ユーザーが今見ているか後で戻ってきたかにかかわらず、質問を後でチェックできるように明示する。

### 2. 言語を選択

ホストプロジェクトが使用するものを使用。プロジェクトに明確なランタイムがない場合（例：ドキュメントリポジトリ）、尋ねる。

プロジェクトの既存のツール規約に従う — プロトタイプのためだけに新しいパッケージマネージャやランタイムを追加しない。

### 3. ポータブルなモジュールにロジックを分離

実際のロジック — 質問に答えている部分 — を小さく純粋なインターフェースの背後に置き、後で取り出して実際のコードベースにドロップできるようにする。周囲のTUIは使い捨て。ロジックモジュールはそうあるべき。

適切な形状は質問に依存：

- **純粋なリデューサー** — `(state, action) => state`。アクションが離散的で状態が単一の値の場合に適する。
- **状態マシン** — 明示的な状態と遷移。「今どのアクションが合法か」が質問の一部の場合に適する。
- **プレーンなデータ型に対する少数の純粋関数**。暗黙の現在の状態がなく、変換だけの場合に適する。
- **明確なメソッド面を持つクラスまたはモジュール**（ロジックが本当に継続的な内部状態を所有する場合）。

質問に最も適合する形状を選ぶ — TUIに配線しやすいもの*ではなく*。純粋に保つ：I/Oなし、ターミナルコードなし、制御フローに`console.log`なし。TUIがインポートして呼び出す。逆方向のフローはない。

これがプロトタイプを自身の寿命を超えて有用にするもの。質問が答えられた後、検証済みのリデューサー/マシン/関数セットは実際のモジュールにリフトされる — TUIシェルは削除される。

### 4. 状態を露出する最小のTUIを構築

**軽量TUI**として構築 — 毎ティックごとに画面をクリア（`console.clear()` / `print("\033[2J\033[H")` / 類似）してフレーム全体を再レンダリング。ユーザーは常に1つの安定したビューを見るべきで、増え続けるスクロールバックではない。

各フレームは次の2つの部分から成り、この順序：

1. **現在の状態**、pretty-printされてdiffしやすい形式（1行に1フィールド、またはフォーマットされたJSON）。フィールド名やセクションヘッダーに**太字**、重要度の低いコンテキスト（タイムスタンプ、ID、派生値）に**暗く**を使用。ネイティブなANSIエスケープコードで可 — `\x1b[1m` 太字、`\x1b[2m` 暗く、`\x1b[0m` リセット。プロジェクトに既にない限りスタイリングライブラリを導入する必要はない。
2. **キーボードショートカット**、下部にリスト：`[a] ユーザー追加  [d] ユーザー削除  [t] クロック進める  [q] 終了`。キーを太字、説明を暗く、またはその逆 — 読みやすければどちらでも。

動作：

1. **状態を初期化** — 単一のメモリ内オブジェクト/構造体。開始時に最初のフレームをレンダリング。
2. **一度に1キーストローク（または1行）を読み取り**、状態を変更するハンドラーにディスパッチ。
3. **完全なフレームを再レンダリング** — 各アクションの後。追加ではなく置き換え。
4. **終了までループ。**

フレーム全体が1画面に収まるように。

### 5. 1コマンドで実行可能に

プロジェクトの既存のタスクランナー（`package.json`のscripts、`Makefile`、`justfile`、`pyproject.toml`）にスクリプトを追加。ユーザーは`pnpm run <prototype-name>`または同等のコマンドを実行するべき — パスを覚える必要はない。

ホストプロジェクトにタスクランナーがない場合、プロトタイプのREADMEの先頭にコマンドを書く。

### 6. 引き渡す

実行コマンドをユーザーに伝える。ユーザー自身で操作する。面白い瞬間は「ちょっと、それは可能であるべきじゃない」や「あれ、Xは違うと思ってた」と言った時 — それらは_アイデア_のバグであり、それがポイント。新しいアクションの追加を希望すれば追加する。プロトタイプは進化する。

### 7. 答えをキャプチャ

プロトタイプが役割を果たしたら、質問への答えだけが残す価値がある。ユーザーがいる場合、何を学んだか尋ねる。いない場合、プロトタイプの隣に`NOTES.md`を残し、プロトタイプが削除される前に答えを記入できるようにする（または、セッションを見ていた場合は自分で記入）。

## アンチパターン

- **テストを追加しない。** テストが必要なプロトタイプはもはやプロトタイプではない。
- **実際のデータベースに配線しない。** 質問が具体的に永続性に関する場合を除き、メモリ内ストアを使用。
- **一般化しない。** 「後でXをサポートしたくなったらどうしよう」はなし。プロトタイプは1つの質問に答える。
- **ロジックとTUIを混ぜない。** リデューサー/状態マシンが`console.log`、プロンプト、ターミナルエスケープコードを参照しているなら、もはやポータブルではない。TUIは純粋なモジュールの薄いシェルとして保つ。
- **TUIシェルを本番に出荷しない。** シェルはターミナルから手で操作されるために最適化されている。その背後のロジックモジュールが残す価値のある部分。
