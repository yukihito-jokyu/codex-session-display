# ADRフォーマット

ADRは`docs/adr/`に配置し、連番を使用する：`0001-slug.md`、`0002-slug.md`など。

`docs/adr/`ディレクトリは遅延して作成 — 最初のADRが必要になったときのみ。

## テンプレート

```md
# {決定の短いタイトル}

{1〜3文：コンテキスト、決定内容、理由。}
```

以上。ADRは単一段落でもよい。価値は、決定が*された*という事実とその*理由*を記録することにある — セクションを埋めることではない。

## オプションのセクション

真の価値を追加する場合のみ含める。ほとんどのADRには不要。

- **Status**フロントマター（`proposed | accepted | deprecated | superseded by ADR-NNNN`） — 決定が見直される場合に有用
- **Considered Options** — 除外された代替案が記憶に値する場合のみ
- **Consequences** — 自明でない下流への影響を指摘する必要がある場合のみ

## 番号付け

`docs/adr/`で既存の最大番号をスキャンし、1つ増やす。

## ADRを提案するタイミング

次の3つがすべて真でなければならない：

1. **元に戻すのが難しい** — 後で考えを変えるコストが意味のある大きさ
2. **文脈なしでは驚くべきもの** — 未来の読者がコードを見て「なぜこんなやり方をしたのか？」と思うだろう
3. **実際のトレードオフの結果** — 本当の代替案があり、特定の理由で1つを選んだ

決定が簡単に元に戻せるならスキップ — 単に元に戻せばいい。驚くべきものでなければ、誰も理由を疑問に思わない。本当に代替案がなければ、「当然のことをした」以上に記録することはない。

### 対象となるもの

- **アーキテクチャの形状。** 「モノレポを使用している。」「書き込みモデルはイベントソーシングで、読み取りモデルはPostgresに投影されている。」
- **コンテキスト間の統合パターン。** 「注文と請求はドメインイベントで通信し、同期HTTPではない。」
- **ロックインを伴う技術選択。** データベース、メッセージバス、認証プロバイダー、デプロイメントターゲット。すべてのライブラリではなく — 交換に四半期かかるもののみ。
- **境界とスコープの決定。** 「顧客データはCustomerコンテキストが所有し、他のコンテキストはIDでのみ参照する。」明示的な「ノー」は「イエス」と同様に価値がある。
- **当然の道からの意図的な逸脱。** 「Xという理由でORMの代わりに手動SQLを使用している。」合理的な読者が反対を想定するであろうものすべて。これらは次のエンジニアが意図的なものを「修正」するのを防ぐ。
- **コードに見えない制約。** 「コンプライアンス要件のためAWSは使用できない。」「パートナーAPI契約のため、レスポンスタイムは200ms以下でなければならない。」
- **除外が自明でない場合の却下された代替案。** 微妙な理由でGraphQLを検討してRESTを選んだ場合、記録する — そうしないと6ヶ月後に誰かがまたGraphQLを提案する。
