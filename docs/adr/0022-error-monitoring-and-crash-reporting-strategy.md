# ADR 0022: エラー監視・クラッシュレポート要否の決定

## ステータス

承認済み

## コンテキスト

Wails (Go + React) を用いたデスクトップアプリケーション開発において、アプリケーションでエラーやクラッシュが発生した際の監視・収集戦略を定義する必要がある。
特に、以下の制約と目標のバランスを取る必要がある。

1. **ローカル環境前提（外部送信禁止）**: 要件定義書（§1.4, §3.1）にて、データはローカル完結とし、外部サーバーへのデータ送信は一切行わないことが義務付けられている。
2. **トラブルシューティング性**: エラーや予期せぬ動作不良が発生した際、開発者が原因特定（デバッグ）を行うための十分な情報を収集・確認できる手段が必要である。
3. **ユーザビリティと実装のシンプルさ**: 一般的なエラー監視サービス（SentryやFirebase Crashlytics等）が使えない中で、ユーザーが容易にログへアクセスし開発者に提供できる操作性と、実装の過度な複雑化防止を両立する。

## 決定

### 1. 外部エラー監視・クラッシュレポートサービスの不使用
外部の自動エラー監視サービス（例: Sentry, Datadog, Firebase Crashlyticsなど）は**一切利用しない**。
これにより、アプリケーションから外部インターネットへクラッシュデータやログが自動送信されることを完全に排除し、ローカル完結の機密保持要件を厳格に順守する。

### 2. ローカルでのエラー確認手段の定義
外部監視サービスの代替として、以下の多層的なローカル確認手段を定義・実装する。

*   **ローカル構造化ログ（バックエンド）**
    *   ADR 0021に基づいて実装される `~/.codex-display/logs/app.log` (JSON形式) および標準エラー出力 (stderr) を、トラブルシューティングの主たる情報源とする。
*   **フロントエンドでのエラー画面表示**
    *   IPC通信でのエラー返却（`AppError`）時や、フロントエンド単体での実行例外をキャッチし、ユーザーフレンドリーなエラー画面やトースト通知を表示する。
*   **ログ確認のためのUI支援機能**
    *   フロントエンドのエラー表示画面および設定画面等に、以下の支援機能を配置する。
        1.  **「ログ保存先パスのコピー」ボタン**: クリックするとログファイルの絶対パス（`~/.codex-display/logs/app.log` を展開した絶対パス）をクリップボードにコピーする。
        2.  **「ログフォルダを開く」ボタン**: バックエンドへ新規IPCメソッド `OpenLogDirectory()` を経由して要求を送り、OSの標準ファイラー（MacのFinder、Windowsのエクスプローラー等）でログが格納されているディレクトリを開く。
*   **パニック（致命的クラッシュ）のハンドリング**
    *   Goバックエンドでの `panic` などの致命的なクラッシュに対しては、特別なリカバリー処理（`defer recover()` を用いたログ出力ハンドリング）は実装せず、標準エラー出力（OSのコンソール）への出力に任せる。実装の複雑化を避け、シンプルなクラッシュ挙動とする。

### 3. 新設するIPCメソッド仕様
ログフォルダを開くために、以下のIPCメソッドをGoバックエンドに追加定義する。

*   **`OpenLogDirectory()`**
    *   **処理内容**: `~/.codex-display/logs/` の絶対パスを決定し、OS標準のコマンド（Mac: `open`、Windows: `explorer`）を非同期実行してフォルダを開く。
    *   **戻り値**: 成功時は無し、失敗時は `AppError`（`INTERNAL_ERROR`）

## 理由

1. **要件（ローカル完結）の厳格な順守**:
   外部のSentryなどのサービスは、開発者のデバッグ効率を大幅に高めるものの、ユーザーデータを外部へ送信するリスク（セッションログに機密コードやトークンが含まれている可能性がある）を排除できないため、不採用とした。
2. **トラブルシューティングと利便性のトレードオフの解消**:
   自動送信は行わないが、エラー画面から「フォルダを開く」や「パスのコピー」をワンクリックで行えるようにすることで、ユーザーが問い合わせの際にログを添付する心理的・操作的ハードルを最小限に抑える。
3. **実装のシンプルさの維持**:
   バックエンドの `panic` は、例外的な致命的状況でのみ発生するものであり、その回復処理やログ保存を一から実装するとコードが複雑化するため、Goのランタイム標準のstderr出力に委ねることで、安全かつシンプルな構成を維持する。

## 検討した代替案

| 代替案 | 内容 | 採用見送りの理由 |
| :--- | :--- | :--- |
| **Sentry等の外部SDK導入** | アプリ起動時にSDKを初期化し、クラッシュ情報を自動でSentryのSaaSへ送信する。 | 「外部サーバーへのデータ送信は行わない（§1.4）」という大前提のセキュリティ・プライバシー要件に明確に違反するため。 |
| **ログを自動でローカルファイルにダンプするパニックリカバリーの実装** | バックエンドのすべてのハンドラーに `recover()` を仕込み、パニック時のスタックトレースを `app.log` に書き込んでから終了する。 | パニックが発生するような致命的状況は極めて稀であり、Wails自体がハンドラーのパニックを一部捕捉してエラーとして扱う仕組みもあるため、独自で複雑なリカバリーロジックを実装するコストと複雑さが見合わないと判断した。 |
| **テキストファイルでのパス案内のみ** | エラー画面に「ログファイルは `~/.codex-display/logs/app.log` です」と書くだけにする。 | パスのコピーやFinderでのオープンを手動で行うのは、ユーザー（特にファイルパスの扱いに慣れていない開発初期のコラボレーターなど）にとって操作が面倒であり、ログ提供の障壁になるため。 |

## 結果

- 外部監視サービスを一切利用せず、ローカルログとUIを通じた手動のトラブルシューティング支援に特化する方針が固まった。
- フロントエンドにおける「ログフォルダを開く」支援ボタンの要件を達成するため、バックエンドにOS標準コマンドでフォルダを開くIPC（`OpenLogDirectory`）を追加設計した。
- これにより、データの外部流出リスクをゼロに抑えつつ、ユーザー起因のエラー調査を実用的なレベルでサポート可能となる。
