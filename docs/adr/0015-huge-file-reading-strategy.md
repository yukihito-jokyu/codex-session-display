# ADR 0015: 巨大ファイル読込におけるストリーミング戦略とバッファ設計

## ステータス

承認済み

## コンテキスト

最大50MBのJSONL形式のセッションログを解析する際、メモリ使用量のスパイクを抑えつつ高速にパースする必要がある。
また、Codex CLIのログレコードにはソースコードや巨大なツール出力が含まれることがあり、1行が非常に長くなる（最大でファイル全体のサイズに匹敵する）可能性がある。

一括読み込み（`os.ReadFile`）と、ストリーミング読み込み（`bufio.Scanner`、`bufio.Reader`）のパフォーマンスおよびメモリ消費量を比較検証し、最適な読み込み戦略と長大な1行への対応方針を決定する必要がある。

## 決定

`bufio.Scanner` を使用した**ストリーミング読み込み（行単位読み込み）**を採用し、バッファ上限サイズをファイルサイズの上限と同じ **50MB** に設定する。

具体的には以下のようにスキャナーを初期化する：
```go
scanner := bufio.NewScanner(file)
buf := make([]byte, 64*1024) // 初期バッファサイズ 64KB
scanner.Buffer(buf, 50*1024*1024) // 最大バッファサイズ 50MB
```

## 理由

1. **高いメモリ効率と低いGC負荷**
   - ベンチマーク検証の結果、55MBのダミーJSONLファイル（最大5MBの行を含む）の解析において、ストリーミング読み込み（`bufio.Scanner`）は一括読み込み（`os.ReadFile`）と比較して**メモリ累積割当量を約35%削減**（111MB → 72.7MB）できた。
   - `bufio.Reader` (`ReadBytes`) を用いた場合は行ごとに新規スライスが確保されて累積割当量が167MBに急増しGCが多発したが、`bufio.Scanner` は内部バッファを再利用するためアロケーション回数を最小限に抑えられる。

2. **動的バッファ拡張による長大行の安全な処理**
   - `bufio.Scanner` はデフォルトの最大行サイズが 64KB に制限されており、これを超えると `ErrTooLong` エラーを返す。
   - 初期バッファを 64KB と小さく保ちつつ、最大制限を 50MB に設定することで、通常行の読み込みではメモリを節約し、巨大な行が出現した時のみ必要に応じてバッファを動的に拡張できるため、長大な行も安全に解析できる。

3. **十分なパフォーマンス**
   - 55MBのファイルを約80msでストリーム読み込みおよびパースを完了でき、要件である「50MBファイルの解析所要時間：10秒以内」を大幅にクリアする。

## 検討した代替案

| 候補 | 採用見送りの理由 |
| :--- | :--- |
| **一括読み込み (`os.ReadFile`)** | 速度は最速（63.8ms）だが、ファイル全体と行分割データの両方をメモリに同時保持するため、メモリ消費量のスパイクが大きくデスクトップアプリのフットプリントに悪影響を及ぼすため。 |
| **`bufio.Reader` (`ReadBytes`)** | ストリーミング読み込みであるものの、行を読み込むたびに新しい byte slice を割り当てるため、累積アロケーション回数が激増（約2万回）し、GC負荷が高まりパフォーマンスを損なうため。 |
