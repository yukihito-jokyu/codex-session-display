# ADR 0019: バッチ検出における `call_id` 非対応・ミスマッチ時のフォールバック方針

## ステータス

承認済み

## コンテキスト

セッションログ（JSONL）のパースおよびバッチ検出（`function_call` / `function_call_output` の紐付け）において、通常は `call_id` フィールドを用いて1:1の対応付けを行う。
しかし、以下のようなケースが発生し、`call_id` による紐付けが正常に行えない可能性がある：
1. 旧バージョンのCodex CLIのログなど、すべてのレコードで `call_id` フィールド自体が存在しない、または空である場合（ケースA）。
2. CLIの不具合やログの破損、一部ツールの仕様等により、一部のレコードのみで `call_id` が欠損または不一致である場合（ケースB）。
3. バッチ内で `function_call` の個数と `function_call_output` の個数が一致しない場合（ケースC）。

これらの状況が発生した際に、パースを中断するのではなく、最大限許容（Tolerant）してパースを継続しつつ、妥当なフォールバック処理を行うための方針を決定する必要がある。

## 決定

1. **ケースA：すべてのレコードで `call_id` が存在しない場合の処理**
   - 出現順（インデックスベース）で `function_call` と `function_call_output` を 1:1 でマッピングする。
   - 個数が不一致である場合の処理：
     - `function_call` の個数が `function_call_output` より多い場合（結果不足）：対応する結果レコードが存在しない `function_call` の output には `null` を設定する。
     - `function_call` の個数が `function_call_output` より少ない場合（結果過剰）：マッピングされず余剰となった `function_call_output` は破棄（無視）する。

2. **ケースB：一部のレコードのみで `call_id` が欠損または不一致の場合の処理**
   - まず、`call_id` が完全に一致するペアについて優先的にマッピングを行う。
   - `call_id` で紐付けられなかった残りの `function_call` と `function_call_output` について、出現順（インデックスベース）で順次マッピングを試みる。
   - 個数が不一致である場合の処理（ケースAと同様）：
     - `function_call` の余剰分：output に `null` を設定する。
     - `function_call_output` の余剰分：破棄（無視）する。

3. **フォールバック時のログ出力レベルの決定**
   - 上記のフォールバック処理（インデックスベースでのマッピング、outputの `null` 設定、または過剰outputの破棄）が発生した際は、**Warn（警告）レベル**でログを出力する。
   - パース処理自体は中断せず、正常に継続する。

## 理由

1. **堅牢性とユーザビリティの重視 (ADR 0009 準拠)**:
   - 一部のログファイルに不備がある、あるいはバージョン差異があるというだけでファイル全体のロードを失敗させるのは、ユーザー体験（UX）を損なう。可能な限りパースを継続する方針をとる。
2. **直感的かつシンプルな紐付けルール**:
   - `call_id` が欠損している場合、基本的には「呼び出された順番に結果が返ってくる」という時系列的な順序性を信じるのが最も妥当であるため、インデックスベースの出現順マッピングを採用した。
3. **個数不一致時の表示整合性**:
   - 呼び出し（`function_call`）が余る場合、フロントエンドに「呼び出した事実」を表示するノードを残しつつ、結果が取得できなかったことを `null` (空) で示すのが適している。
   - 呼び出し先が不明な結果（`function_call_output`）のみが余る場合、それを画面に浮いたノードとして配置するとユーザーが混乱するため、警告ログを残して破棄するのが安全である。
4. **警告ログによる診断容易性**:
   - ログに `Warn` レベルで出力しておくことで、必要に応じて開発者がデータ整合性の問題を後から調査できるようにする。

## 検討した代替案

| 案 | 内容 | 採用見送りの理由 |
| :--- | :--- | :--- |
| **厳格モード（エラー中断）** | 対応が取れない時点で `PARSE_ERROR` を返して終了する。 | 軽微な破損や古い形式のファイルが全く閲覧できなくなるため、許容（Tolerant）パース方針に反する。 |
| **余剰結果の個別ノード化** | 対応する call がない `function_call_output` を、ハーネス外（分岐）の単独ノードとして配置する。 | 呼び出しコンテキストが一切不明な結果ノードがグラフ上に浮遊することになり、画面表示が乱れ、ユーザーの混乱を招くため。 |
