# ADR 0013: Go 依存ライブラリの選定（JSONパーサー、ロガー）

## ステータス

承認済み

## コンテキスト

Wails (Go + React) を用いたデスクトップアプリケーション開発において、バックエンド（Go）で使用する依存ライブラリを選定する必要がある。
特に、以下の2つの選定が重要となる。
1. **JSONパーサー**: 最大50MBに達するJSONL形式のセッションログを高速かつ効率的にパースし、React Flow用の構造体にデコードする。
2. **ロガー**: バックエンドの動作ログや警告、エラー情報を構造化データとして適切に出力・追跡する。

選定にあたっては、以下の基準を満たす必要がある。
- **プラットフォーム互換性**: 各OS（macOS/Windows/Linux）でCGOなしでビルド可能であること。
- **依存関係の最小化**: 不要なセキュリティリスクやビルド複雑化を防ぐため、外部ライブラリへの依存は最小限に留める。
- **パフォーマンスと応答性**: デスクトップアプリとしての快適な動作（ミリ秒レベルのログ読み込み）を実現できること。

## 決定

以下のライブラリを採用する。

1. **JSONパーサー**: `github.com/goccy/go-json`
2. **ロガー**: 標準ライブラリ `log/slog`

## 理由

### 1. JSONパーサー: `github.com/goccy/go-json`
- **高速性とUI応答性**: 標準の `encoding/json` に対して約4.7倍高速であり、メモリ使用量やアロケーション回数も大幅に削減される。10MB規模のデータ（約6.25万行）を用いた二段階パースのベンチマーク測定では、`encoding/json` が約266ms要するのに対し、`go-json` は約55.8msで完了した。これを最大想定の50MBファイルに換算すると、標準ライブラリの約1.33秒から約279ミリ秒へと短縮され、UIのもたつきを効果的に解消できる。
- **完全な互換性**: 標準の `encoding/json` とドロップイン互換（インターフェースが同一）であるため、コード記述が容易で、万が一将来的に標準ライブラリに戻す場合も移行コストがほぼゼロである。
- **純粋なGo実装**: CGOを必要としないため、Wailsのクロスビルド環境でも問題なく動作する。

### 2. ロガー: 標準ライブラリ `log/slog`
- **十分な機能とゼロ外部依存**: Go 1.21から導入された標準の構造化ロガーであり、キーバリュー形式やJSON形式のログを標準機能だけで出力できる。外部のサードパーティライブラリ（ZapやZerolog等）を依存関係に追加する必要がない。
- **柔軟なカスタマイズ性**: `slog.Handler` インターフェースを実装することで、フロントエンド（Wails）側へのログリアルタイム転送や、ローカルファイルへの書き出しなどを容易に拡張できる。

## 検討した代替案

| カテゴリ | 候補 | 採用見送りの理由 |
| :--- | :--- | :--- |
| **JSONパーサー** | `encoding/json` (標準) | 十分に安定しているが、リフレクションのオーバーヘッドが大きく、大容量ログのデコード時にUIスレッドを長くブロッキングする懸念があるため。 |
| **JSONパーサー** | `bytedance/sonic` | 速度は最速クラスだが、JITコンパイルを使用する特性上、アーキテクチャやOSの制限（一部環境での非対応）があり、ポータビリティとビルド安定性の面で懸念があるため。 |
| **ロガー** | `uber-go/zap` / `zerolog` | パフォーマンスは極めて優秀だが、デスクトップアプリのバックエンド用途としては `slog` で十分であり、外部依存を増やしてまで導入するメリットが薄いため。 |

## 結果

- JSONL解析の速度向上が見込める一方で、不要なサードパーティ製ライブラリの依存を最小限（`go-json` のみ）に抑えた、クリーンでポータブルなバックエンド構成が確立された。
