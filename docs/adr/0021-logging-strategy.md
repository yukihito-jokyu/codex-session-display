# ADR 0021: Go バックエンドにおけるロギング戦略の決定

## ステータス

承認済み

## コンテキスト

Wails (Go + React) を用いたデスクトップアプリケーション開発において、バックエンド（Go）での適切なロギング戦略を定義する必要がある。
特に、以下の3つの観点からロギング仕様を固めることが求められる。
1. **ログレベルの定義と出力基準**: 各動作状況やエラーに対し、どのログレベル（DEBUG, INFO, WARN, ERROR）を適用するか。
2. **出力先とフォーマット**: 開発時と本番（デスクトップアプリ単体起動）時でのログの出力先（コンソール、ファイル）およびフォーマット（テキスト、JSON）の設計。
3. **パース警告ログのフォーマット**: `tolerant` パースや `call_id` 欠損時のマッピング等の不整合が発生した際、診断に必要な情報をログサイズ肥大化や秘匿情報漏洩を防ぎつつ含める設計。

## 決定

### 1. ログレベルと出力基準
Go標準ライブラリの `log/slog` を使用し、以下の基準でログレベルを使い分ける。

*   **`DEBUG`（デバッグ情報）**
    *   開発・トラブルシューティング用の詳細ログ。
    *   出力基準: JSONLパースの各行の処理進捗、キャッシュ処理の詳細、内部レイアウト計算のステップなど。
    *   *※通常（本番ビルド）は出力されず、デバッグモード時のみ有効化する。*
*   **`INFO`（通常動作の記録）**
    *   アプリケーションの正常な動作を示すイベント。
    *   出力基準: アプリ起動/終了、JSONLパースの開始と成功（処理行数や所要時間、ノード数等のサマリー）、キャッシュの読み込み成功など。
*   **`WARN`（回復可能な問題 / データの不整合）**
    *   処理自体はフォールバック処理等によって継続可能だが、入力データに不整合や軽微な異常がある場合。
    *   出力基準: 1行パース失敗による該当行のスキップ、`call_id` の不整合によるインデックスベースの紐付け（フォールバック）発生、`turn_context` 重複による上書き、`session_meta` 欠損時のファイル名からのメタデータ推測など。
*   **`ERROR`（回復不可能な問題 / 主要機能の失敗）**
    *   処理の継続が不可能な場合、あるいは主要機能（キャッシュ等）が完全に失敗した場合。
    *   出力基準: JSONLファイルの読み込みエラーによるパース中断、パース不正レコード率が50%を超えたことによる処理中断、キャッシュファイル（`~/.codex-display`）の書き込み/読み込み失敗など。

### 2. 出力先とフォーマット
動作環境（開発時/本番時）およびビルド設定に応じてログの出力先とフォーマットを切り替える。

| 実行環境 | 出力先 | フォーマット | 理由 |
| :--- | :--- | :--- | :--- |
| **開発時 (`wails dev`)** | 標準エラー出力 (stderr) | テキスト形式 (`slog.TextHandler`) | 開発用ターミナルで人間が読みやすく、リアルタイムで把握しやすいため。 |
| **本番時 (パッケージ版)** | 標準エラー出力 (stderr)<br>および ファイル出力 (`~/.codex-display/logs/app.log`) | JSON形式 (`slog.JSONHandler`) | デスクトップアプリ単体起動でもログを保存し、不具合時の問い合わせ用ログとして活用。構造化ログ（JSON）にすることで機械可読性を確保。 |

### 3. パース警告ログのフォーマット
`WARN` レベルのパース警告について、構造化ログのキー名と値のルールを以下のように統一する。

#### ① 1行のJSONパース失敗時
*   **メッセージ**: `failed to parse JSONL line, skipping`
*   **構造化項目**:
    *   `file_path` (string): 対象ファイルの絶対パス
    *   `line_number` (int): 失敗した行番号（1-indexed）
    *   `error` (string): エラーメッセージ詳細
    *   `line_preview` (string): 失敗した行の**先頭100文字**
        *   *※巨大な行データによるログサイズ肥大化や、トークン等の秘匿情報流出を防ぐため、先頭100文字のプレビューに制限する。*

#### ② `call_id` 不整合によるインデックスベース紐付け発生時
*   **メッセージ**: `call_id mismatch or missing, falling back to index-based mapping`
*   **構造化項目**:
    *   `file_path` (string): 対象ファイルの絶対パス
    *   `turn_id` (string): 対象のターンID
    *   `call_count` (int): 当該ターンの `function_call` レコード総数
    *   `output_count` (int): 当該ターンの `function_call_output` レコード総数
    *   `details` (string): マッピング処理結果（例: `"matched: 3, null_assigned: 1, discarded: 0"`）

#### ③ `turn_context` 重複による上書き発生時
*   **メッセージ**: `duplicate turn_context encountered, overwriting`
*   **構造化項目**:
    *   `file_path` (string): 対象ファイルの絶対パス
    *   `turn_id` (string): 対象のターンID
    *   `line_number` (int): 重複が検出された行番号

#### ④ `session_meta` 欠損によるファイル名からの推測時
*   **メッセージ**: `session_meta is missing, estimating session metadata from file name`
*   **構造化項目**:
    *   `file_path` (string): 対象ファイルの絶対パス
    *   `estimated_session_id` (string): ファイル名から推測したセッションID
    *   `estimated_timestamp` (string): ファイル名から推測したタイムスタンプ

### 4. エラーエスカレーションとログ出力箇所の一元化
ログの重複（ダブルロギング）によるログの可読性低下を防ぎ、スタックトレース等の文脈を明確に保つため、エラーとログの出力箇所に関して以下のエスカレーションルールを設ける。

*   **`ERROR`レベルログの一元化**:
    *   `Repository` 層や `Usecase` 層などの内部レイヤーで発生した致命的エラーは、その場ではログ（`slog.Error`）を出力せず、Go標準のエラーラッピング（`fmt.Errorf("context: %w", err)`）を使用して上位レイヤーへ伝播させる。
    *   最外周の **`App` レイヤー（WailsのIPCハンドラーがある `app.go` など）において、伝播されたエラーを一括して `slog.Error` でログ出力** し、フロントエンドへエラーレスポンスを返却する。
*   **`WARN` / `INFO` / `DEBUG`レベルログの即時出力**:
    *   エラー伝播を伴わない警告や通常イベント（処理を継続するパース行スキップ警告、`call_id` の不整合警告、キャッシュ成功情報など）については、**発生したレイヤー（RepositoryやUsecase等）の処理内でその場で即時出力** する。

## 理由

1. **開発容易性と本番トラブルシューティング性の両立**:
   - `slog` の柔軟なハンドラー切り替えを利用し、開発中はプレーンテキストで素早くデバッグしつつ、本番では構造化ログファイルを出力することで、ユーザーの不具合解析に必要な情報を確実に収集できるようにした。
2. **ログの安全性とパフォーマンスの担保**:
   - パースエラー行の `line_preview` を先頭100文字に制限することで、数MBに及ぶ巨大なエラー行がそのままログに出力されてディスク容量やI/Oを圧迫するのを防ぎ、同時に不要な機密情報がログに残るリスクを軽減した。
3. **エラーハンドリングの一貫性**:
   - キャッシュの読み書き失敗は、メモリ内処理によってアプリ自体は動作を継続できる（フォールバック可能）ものの、本来期待されるキャッシュ機能という主要要件の失敗であるため `ERROR` として記録し、管理者がディスクI/O等のシステム異常を即座に検知できるようにした。
4. **エラーログ一元化によるダブルロギングの防止と明瞭化**:
   - 各層でエラーログを出力し、さらにエラーを返して上位でも出力すると、1つのエラーに対して大量の重複ログが記録される。エラー伝播によるコンテキスト保持を活用し、最上位層（App層）のみでログ出力することで、クリーンで明瞭なエラー追跡を可能にした。

## 検討した代替案

| 代替案 | 内容 | 採用見送りの理由 |
| :--- | :--- | :--- |
| **生ログ行の全出力** | JSONパースエラー時、該当行を丸ごとログに出力する。 | エラーが発生したレコードが巨大な場合、ログファイルが急速に肥大化し、ディスク圧迫やメモリ負荷を引き起こすリスクがあるため。また、秘匿情報の漏洩リスクも高まる。 |
| **本番ログもテキスト形式** | 本番ログファイルも人間が見やすいテキスト形式で出力する。 | ログファイルの量が多くなった際に、エラー分析スクリプトやパースツールによる自動集計・追跡が難しくなるため。構造化ログ（JSON）に統一する方が運用性が高い。 |
| **キャッシュ失敗をWARNとする** | キャッシュ読み書き失敗は動作を継続できるためWARNレベルとする。 | キャッシュはパフォーマンス目標（§3.2）を達成するための極めて重要な機能であり、その失敗は一時的なデータ警告とは異なり、システム環境（ファイル権限不足等）の根本的な異常を示すため、ERRORレベルで通知すべきと判断した。 |
| **各層でのエラーログ出力** | 各レイヤー（Repository/Usecase）でエラーを検知した時点で都度ERRORログを出力する。 | 1つのエラーに対して各層で重複したログ（ダブルロギング）が吐き出され、ログファイルが散乱してトラブルシューティングの妨げになるため。 |


## 結果

- Goバックエンドの堅牢なロギング方針が策定され、`log/slog` に基づく具体的なログ定義・出力基準・警告フォーマットが定義された。
- これにより、大容量のセッションログ解析においてトラブルシューティング性と安全性を両立するロギングが実装可能となる。
