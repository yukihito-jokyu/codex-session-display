# ADR 0018: フロントエンド静的ファイルの埋め込み方式の決定

## ステータス

承認済み

## コンテキスト

Wails (Go + React) を用いたデスクトップアプリケーションにおいて、プロダクション環境（本番配布時）におけるフロントエンド静的ファイル（HTML/CSS/JS/画像等）の配信方式を決定する必要がある。
特に「単一の実行可能バイナリとして配布可能であること」「配布先での追加ファイルやランタイムへの依存性を排除すること」という要件を満たす必要がある。

## 決定

1. **`embed.FS` 方式の採用**:
   - Goの `embed` パッケージの `embed.FS` を使用し、ビルド時にフロントエンドのコンパイル成果物（`frontend/dist` 配下）を Go バイナリ内に完全に埋め込む。
2. **Wails起動オプションへのバインド**:
   - 埋め込んだ `embed.FS` を Wails 起動オプション（`options.App`）の `Assets` フィールドに指定し、WebView がアプリ内部のメモリ空間からリソースを安全かつ高速にロードできるようにする。
3. **ビルドプロセスの自動シーケンス定義**:
   - `wails build` コマンドを通じて、以下の順序でビルドが実行されることを前提・保証する。
     1. フロントエンド of ビルド（Viteによる `npm run build`）による `frontend/dist` へのアセット出力。
     2. Go コンパイラによる `frontend/dist` の埋め込み（`//go:embed`）および Go バイナリのビルド。

## 理由

1. **単一バイナリ配布要件の完全な充足**:
   - すべてのリソースがバイナリに内包されるため、ユーザーには一つの実行可能ファイル（macOSの `.app` や Windowsの `.exe`）のみを提供すればよく、インストーラーの簡素化やポータビリティが最大化される。
2. **実行時パス依存の排除**:
   - アプリの起動場所やカレントディレクトリ、配置パスに関わらず、常にバイナリ内部のメモリからリソースを安定してロードできるため、パス解決に起因するバグを未然に防ぐことができる。
3. **開発者体験（DX）への影響ゼロ**:
   - 本番ビルド時には埋め込みのオーバーヘッドが発生するが、開発時は `wails dev` によりViteのホットリロードサーバー（HMR）経由で実行される（ADR 0017参照）ため、開発時のフィードバックサイクルを犠牲にしない。

## 検討した代替案

| 候補 | 採用見送りの理由 |
| :--- | :--- |
| **外部ファイルパス指定方式** | バイナリとは別に `frontend/dist` ディレクトリを同梱して配布し、Go側で `http.FileServer` 等を使ってローカルパスから配信する方式。バイナリ自体は軽量化できるが、配布時に複数ファイルの管理が必要となり、ユーザーの実行パスに依存するバグが発生しやすい。また、「単一バイナリ配布」の要件に反するため見送った。 |
